# Review of the plan, 6 September 2026

A final critical read of everything decided so far, before any code is written. Each finding says
what is wrong, how it was established, what it costs if left, and what to do. Numbered so they can
be referred to. Severity is about consequence, not effort.

The implementation plan that results is in [[implementation-plan]].

---

## Critical: would have produced wrong fiscal records or lost invoices

### R1. Shadow mode as designed would issue real invoices

**What the plan said.** Run Litmind against Numbers v2 in "shadow mode", issuing into a throwaway
series and discarding the result, to exercise the real code path with no fiscal consequence.

**What the AEAT says** (developer FAQ, section 11): a SIF operating against the production
environment **cannot produce test invoices**. Any invoice it generates is real, gets a real record
submitted, and must then be annulled with a further record:

> no está aceptado en la normativa que un SIF operativo que factura "en real" [...] pueda producir
> "facturas ficticias" [...] deberá procederse a la inmediata posterior anulación de ellas

A throwaway series against production would have written hundreds of real records into the chain
and to the AEAT, each needing an annulment record afterwards.

**Fix.** All rehearsal targets the AEAT **pre-production environment** (`prewww2.aeat.es`, "Anexo I:
entorno de PRUEBAS" in the web service specification), which exists precisely for this, still
requires the real qualified certificate, and has no fiscal effect. And a rehearsal chain is a
separate chain that is **wiped before go-live**, so the first real record is `PrimerRegistro: S`
and chains to nothing.

This also gives the owner what they asked for: a full Litmind plus Numbers v2 environment on the
development machine, issuing test invoices the AEAT test service actually receives.
See [[implementation-plan#Phase 2]].

### R2. Litmind's queue can lose an issuance command without a trace

**What the plan assumes.** Litmind queues an `IssueInvoice` command on its ServiceBus with the
charge id as idempotency key; a Numbers outage delays invoices but never loses them.

**What the ServiceBus actually does** (`app/src/ServiceBus/CLAUDE.md`, marked "still open"):
publishes are fire-and-forget with no publisher confirms, and a message written into a
not-yet-noticed dead broker connection **is lost silently**. This has already happened in
production (an achievements backfill, July 2026). Separately, `make redis-flush-all` drops queued
messages, and messages **can be redelivered**, which the note explicitly says handlers must
tolerate.

So without a change, some successful charges would produce no invoice, and nothing would notice.

**Fix, two parts.** (a) A **transactional outbox in Litmind**: the command is written to a database
table in the same transaction as the payment record, and a relay publishes it. Nothing is lost
between "the charge succeeded" and "the command exists". (b) A **charge-to-invoice reconciliation
job**: every successful Stripe charge and every PayPal transaction has exactly one invoice at
Numbers v2. The plan had this only for refunds; it is more important for issuance, because a missing
invoice is silent and a missing rectificativa at least has a refund pointing at it.

Redelivery was already covered: it is why Numbers' idempotency is load-bearing.

### R3. PayPal is live and the design only mentions Stripe

459 invoices since 1 January 2025 carry a `payment_id` and no Stripe charge id. The `payments` table
has `paypal_txn_id`. PayPal is not history: it is roughly ten percent of current invoicing.

The idempotency key, the external references, the webhook trigger for rectificativas and the
reconciliation job are all written around Stripe. **PayPal is a second first-class payment source**,
with its own transaction id as idempotency key and its own IPN as the trigger. Every one of those
places needs the second case. This is also the source of the January 2026 duplicates, so it is not
the path to leave under-designed.

### R4. Ninety-three percent of invoices have no customer tax id, and that decides F1 versus F2

54,964 of 58,807 invoices have an empty `customer_dni_nif_cif`; 53,199 of those are to customers
resident in Spain. For history it does not matter. For issuance under Verifactu it decides which
kind of invoice these are.

A complete invoice (`F1`) identifies its recipient. A **simplified invoice (`F2`)** does not, and is
permitted below a value threshold that every Litmind membership sits under. The plan currently says
"we never issue F2" and dismissed `R5` (rectificativa of simplified invoices) as inapplicable. **If
consumer invoices should be F2, that reverses**: `R5` becomes the refund code for the majority of
invoices, and the recipient block is omitted rather than half-filled.

This is the single most consequential question for the gestor and it was not on the list. It
changes the record shape, the correction codes, and the PDF. See
[[implementation-plan#Questions that gate a phase]].

### R5. Issuer identity is not in old Numbers, and it has changed ten times

The migration source of record is old Numbers, which has no issuer fields at all. Litmind's
`invoices` table stores the issuer's name, address and tax id **per row**, and across the history
there are **ten distinct identities**: two spellings of the name, five addresses, and four formats
of the same NIF. A re-rendered 2015 PDF must show the 2015 address, not today's.

Worse: **6,343 invoices between December 2024 and January 2026 carry the NIF as `ES J39898734`**,
with the letter in the wrong place. That is a printed error on a year of invoices. It is not
correctable, but it is the kind of thing worth knowing before an inspection asks.

**Fix.** Issuer identity becomes the **fourth** field Litmind supplies to the migration. Store the
historical display value as printed, and separately one canonical NIF (`39898734J`) for the
Verifactu records going forward.

### R6. The invoice command is not a queued command today

Everything about the cutover being "a consumer pause" assumes `IssueInvoice` is a queued command.
Today `invoices::create()` is called **synchronously** inside the Stripe webhook, the PayPal IPN
handler, the refund path, the credit-pack service and a service tool. The refactor that makes
issuance a command is a **prerequisite of the cutover strategy**, and it was in the architecture but
not in the prerequisite list. It is now [[implementation-plan#Phase 1]].

## Serious: would have caused a compliance or operational failure later

### R7. The AEAT flow-control rule was not designed for

Article 16.2 of the order, restated in the web service specification: after every submission the
AEAT returns `TiempoEsperaEnvio`, initially **60 seconds**, and the system **must not submit again**
until either that many seconds have passed or **1,000 records** have accumulated. The value can
change with each response and must be honoured.

The plan's "table and a polling worker" outbox is still right, but the worker has to be a
**batching, throttled sender that reads the wait time from each response**, not a per-record loop.
At fifteen invoices a day this is one batch a minute at most, but a naive implementation would be
rejected on its second invoice.

### R8. Voluntary early submission may bind us, which would end rollback at cutover

The plan's rollback story assumes we can revert to local issuance any time before 1 July 2027. The
developer FAQ says nothing about whether **starting** VERI\*FACTU submission early commits the
taxpayer for the calendar year. Under the sister regime (SII) it does. **If it does here, rollback
ends at cutover, not at the deadline**, and the only safe rehearsal is against pre-production.

Not a change to the plan (R1 already moves rehearsal to pre-production), but a change to what
"rollback" means, and a question for the gestor before the cutover date is fixed.

### R9. The golden-file export test would put real customer data in git

The plan pins Victor's export format with a golden-file test against `contab-loren.xlsx`, which is
a real export containing real client names and tax ids. Committing it as a fixture is exactly the
"personal data in git history is permanent" mistake the plan warns about elsewhere.

**Fix.** The fixture is generated from **synthetic** data in the test itself, and the test asserts
structure, types, formulas, widths and the blank-row rhythm. The real export is compared against the
old system's real export **once, by hand, during migration rehearsal**, and never committed.

### R10. The API has no way to find the invoice for a given payment

Litmind stores no invoice data, so "show the invoice for this payment" needs a lookup by the
external reference. `listInvoices` by customer and `getInvoice` by code are not enough. Add
`getInvoiceByExternalReference(provider, kind, id)`. Cheap, and everything about the account page
depends on it.

### R11. Old Numbers has three more tables the migration does not mention

`expenses` (1,504 rows, with a `deductiblePercentage`), `financial_balances` (a manual snapshot of
Stripe, PayPal, Bankinter, Vivid and cash balances over time), `annotations` (4 rows, timeline
markers), and `providers`. All small, all needed, none in the reconciliation report. Add them, with
the same count-and-sum checks.

### R12. The invoice email attachment path has to be rebuilt

Litmind's email pipeline attaches invoices by `attachedInvoiceId`, a local row id, rendering at send
time. After the cutover there is no local row. The attachment mechanism becomes "fetch this invoice's
PDF from Numbers v2 by code at send time". Small, but it is on the critical path of every invoice
email and it was not listed.

### R13. Certificate, SIF identification and the declaración responsable are not tasks

Three things every submission needs and nothing in the plan schedules:

- **The qualified certificate** of the obligado tributario, installed where Numbers v2 can sign
  with it. Obtaining one has lead time; **it expires** (FNMT persona física certificates typically
  every four years), so renewal is an operational calendar entry, not a one-off; and a copy has to
  exist outside the cluster, or losing the secret store means re-issuing under time pressure.
- **The SIF's own identification** in every record: developer NIF, name, id, version, installation
  number. Trivial to build, but the values have to be decided.
- **The declaración responsable**. For own-use software the taxpayer signs it. It is a document that
  has to exist by go-live.

### R14. `NUMBERS_IS_ACTIVE` is off in development

`NUMBERS_IS_ACTIVE = !IS_DEVEL_ENVIRONMENT` in Litmind's config, so on the development machine
Litmind never talks to Numbers at all. The dev-phase environment needs this on, pointed at the local
Numbers v2, which also means the dev `.env` needs a source credential. Small, but it is the first
thing that would have "not worked" in Phase 2.

## Improvements: worth doing, not dangerous

### R15. Invoice date must be Spanish local date, by rule

Litmind stores UTC. The fiscal date (and the year in the code) must be Europe/Madrid. Checked: **no
historical invoice straddles a year boundary** between the two, so the migration is safe. Going
forward the rule has to be explicit, because an invoice at 23:30 UTC on 31 December is next year's.

### R16. The dashboard backlog count in the top bar is shown to users who cannot act on it

Show it only to holders of `verifactu.operate`. Everyone else sees a number they can do nothing
about.

### R17. Sentry and metrics

Numbers v2 should report to the existing self-hosted Sentry (`sentry.tin.cat`) as its own project,
and expose the submission backlog, refusals, and rejection counts as Prometheus metrics, since the
scrape infrastructure already exists for Litmind. Alerting on "backlog older than one hour" is the
single most useful alert in the system.

### R18. Turnstile and the API

Obvious once stated: Turnstile is for the human forms only. The source API must never see it.

### R19. The `payment_id` link and zero-value invoices

Litmind skips invoice creation when the Stripe total is zero (a fully discounted period). Whether a
zero-value supply still needs an invoice is a gestor question; low stakes, but it should be asked
rather than inherited.

### R20. Consumer invoices and OSS

If EU consumers keep being charged Spanish VAT (tax determination row 2), the EU One Stop Shop
threshold question exists at some volume. Almost certainly not at this one, but it belongs on the
gestor list rather than being assumed away.

## What held up

Worth recording, so the review is not read as "everything was wrong":

- The single-SIF decision, the no-local-copies decision, and retention living with the chain all
  survived contact with the AEAT documentation intact, and in two cases were strengthened by it
  (generation order is a stated requirement; VERI\*FACTU-only removes two obligations).
- The money model needed nothing changed.
- The measured data (volume, series integrity, currencies) was the right thing to have done first;
  five of the findings above came from querying it rather than from reading the plan.
